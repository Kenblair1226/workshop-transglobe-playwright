單元 A · Playwright 10 / 32

可靠性原則

先消除 flake，再談大量平行

01語意 locator描述使用者意圖，不綁 DOM 順序。
02Web-first assertion等待真實狀態，不使用固定 sleep。
03測試隔離不依賴順序、不共享可變狀態。
04確定性資料輸入與商業結果可預測、可清理。
05Retry 是訊號用來分類 flaky，不用來掩蓋根因。
單元 A · Playwright 11 / 32

結果分析

先分類結果，再決定下一個動作

PASS首次即通過符合預期，仍要關注耗時與涵蓋缺口。
FAIL確定性失敗Assertion、應用、環境或資料與預期不符。
FLAKYRetry 後通過Playwright 的 flaky 分類；必須追根因。
SKIP未執行不是綠燈證據，必須說明條件與 owner。
SLOW通過但太慢拖長 feedback loop，也提高雲端執行成本。

問題診斷

Report → Trace → Root cause

  • 1Report：定位第一個失敗 assertion、project、retry 與附件。
  • 2Trace：沿 timeline 找最後成功動作與失敗前後頁面狀態。
  • 3證據：比對 DOM snapshot、network、console、影片與截圖。
  • 4歸因：application defect、test assumption、data 或 environment。

Readiness gate

穩定性與平行安全，是兩個不同 gate

1Local green先確認單次執行正確
2Repeat ×3retries=0 · 檢查一致性

單元 B · 應用程式現代化

舊有 Java 現代化為何停滯

01到處都是 Java 8核心服務仍停在主流支援已結束的語言版本。
02Spring Boot 2.x 已 EOL安全性修補停止，未處理的 CVE 持續累積。
03javax → jakarta 斷層Namespace 更名幾乎影響每一個 import。
04脆弱的回歸測試套件低覆蓋率讓每次升級都像在賭博。
05口耳相傳的知識知道「為什麼」的工程師早在兩次組織重整前離開。
06稽核軌跡要求法遵要求每項正式環境變更都要有證據。
單元 B · 應用程式現代化 22 / 32

單元 B · 應用程式現代化

升級不只一種，每種都需要不同計畫

01相依套件版本提升Patch／minor 版本，通常是機械式修改。
02框架主版本升級Spring Boot 2 → 3，包含 breaking change 與設定重寫。
03語言版本升級Java 8 → 21，包含新語法與已移除 API。
04CVE 修補由安全風險驅動、限時且高優先。
05Namespace 遷移在整個程式樹將 javax 改為 jakarta。
06測試套件現代化先重建測試覆蓋率，再動其餘程式碼。
